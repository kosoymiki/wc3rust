# WC3 content-model coverage (`wc3-data` + `wc3-formats`)

Owner: layer DATA + FORMATS (ledger 394). Date: 2026-11-15.

Purpose: prove, with numbers and tests, that **every object row the UI/sim can show
resolves a name, an icon, a tooltip, a hotkey, a price and a tech requirement from
the shipped data** — and that every map file variant the corpus contains parses —
so no HUD, shop, tooltip or simulation layer has to guess or hard-code text.

The audit is code, not prose: [`crates/wc3-data/src/coverage.rs`](../../crates/wc3-data/src/coverage.rs)
(`GameDatabase::coverage()` / `menu_coverage()`), rendered by
`cargo run -p wc3-data --example data_coverage`. The tables below are generated by
[`analysis/agent-data/gen_data_coverage.sh`](gen_data_coverage.sh); re-run it after
any loader change instead of editing numbers by hand.

```text
bash analysis/agent-data/gen_data_coverage.sh          # regenerate the generated blocks
CARGO_BUILD_JOBS=2 cargo test -p wc3-data -p wc3-formats --offline   # 206 tests, 14 suites
```

### How to read the gaps

Every value below was verified against the shipped text/sheets; none of them is a
resolution bug the loader could fix.

| Gap | Measured cause (evidence) |
|---|---|
| `ability` 4 rows without a name (`Aalr`, `Asla`, `Asod`, `Attu`) | each row's `code` names itself and no profile section in `analysis/war3_data/Units` carries `Name`/`Tip` for it (`[Asla]` has only `Casterart`) — engine-internal abilities, never on a card |
| `ability` icon/tooltip gaps | the `AC*`/`AI*` variant families inherit from a base that has no `Art` (`[Abli]` = `Name` only); the 56 hero learn buttons — the surface a player actually clicks — are 56/56 complete |
| `buff` 5 without a name (`Arai`, `BNsl`, `BUst`, `Bens`, `Buns`) | The buff section carries `Buffart` only; `Arai` doubles as the ability id whose section holds the name, so the *buff* row is anonymous by data design |
| `buff` 8 without an icon | `BEst`, `BFig`, `BNin`, `BNsp`, `Barm`, `Bdet`, `Beye`, `Brai` have a `Bufftip` but no `Buffart` |
| `item` hotkey 53/132 | RoC assigns `Hotkey=` only to some items (`[phea]` has `Art` only); measured population: 49 `usable=1`, 53 with a hotkey, 113 with an ability. TFT added hotkeys widely |
| `undead/unit` `uplg` without name/icon | `uplg` is the `PlagueWard` stub (`comment(s)=PlagueWard`, `targType=ward`, `InBeta=1`) with no profile section in either shipped text layer — a spell-placed ward, never a card row |
| `upgrade` `Roch` without tip/hotkey | `[Roch]` ships `Name` and `Art` only (`analysis/war3_data/Units/OrcUpgradeFunc.txt:1`) |
| `*/hero` tooltip 3-4 per race | campaign heroes (`Hant`, `Ewar`, `Umal`, …) have no `Tip`/`Ubertip`: they are never trained, so retail wrote none |
| `creeps`/`critters`/`commoner` hotkeys | neutral units are placed by the map, not built; retail gives them no `Hotkey` (61/163 creeps do have one) |
| `other/building` 66 without hotkey | map-placed neutral buildings (taverns, shops, roosts, gates) — no build button exists |
| abilities on `abilList` without card text | `abilList` includes behaviour slots (`Aatk`, `Amov`, `AC*` creep variants) that have no card by design; the audit reports them separately from `heroAbilList` |

## Command card

The card is driven by three profile lists — `Trains`, `Builds`, `Researches` —
resolved into `MenuEntry` values (`crates/wc3-data/src/menu.rs`). The measured
invariant (`tests/data_coverage.rs::card_reachable_rows_resolve_a_name_and_an_icon`):
**every reachable id resolves a name and an icon; every entry resolves name +
icon + gold**.

- 182 entries on RoC (122 train/build + 60 research), all 182 complete.
- 179/182 carry a hotkey. The three that do not (`nfel`, `ninf`, `nbal`, the
  Demon Gate summons) have no `Hotkey` key in `NeutralUnitFunc.txt` /
  `NeutralUnitStrings.txt` at all; the test asserts the row really ships none, so
  a loader regression cannot hide in that number.
- 151 requirement references, 151 display names resolved, 0 unknown ids
  (`Requires` + the `Requirescount`/`Requires1..N` upgrade encoding).
- Hero learn-skill buttons: 56/56 with name, icon, hotkey and tooltip.

## Override semantics (what wins)

Cross-checked end-to-end on `DotF_v1.4.w3x` (a TFT map whose prototype `Ucrl` does
not exist in RoC and has no profile text in the TFT extraction):

1. map `war3map.wts` string (`TRIGSTR_n`) — wins over every profile file;
2. map object data (`war3map.w3u/.w3a/.w3t/...`) — wins over the shipped row;
3. `*Func.txt` — wins over `*Strings.txt` for the same key;
4. `*Strings.txt`.

Fields a map does **not** set are the prototype's (`old_id`) values: `U000`
(base `Ucrl`) resolves its name from the map's `.wts` and its icon only through
the prototype link; `I000` (base `ankh`) does the same. Both are asserted in
`wts_and_object_data_override_the_profile_text`. Buffs behave the same way with
`war3map.w3b` (`Bufftip`/`Buffart` + `fnam`/`fart` overrides).

## Content-model changes in this pass

All in `crates/wc3-data` (formats layer unchanged):

| Change | Reason (measured) |
|---|---|
| `GameDatabase::requirements()` reads `Requires` **and** `Requirescount` + `Requires1..N` | retail upgrades write `Requirescount=3`, `Requires=` (empty), `Requires1=hkee`; the old reader returned an empty list, so every research button lost its prerequisites (`defs.rs` used the same broken read) |
| `UnitView::researches()` + `MenuEntry` research path (`menu_entry`/`research_entry`/`research_menu`, `GameDatabase::researchers()`) | `Researches=` exists in 32 RoC / 41 TFT sections and was not modelled at all: the upgrade tab had no source of truth |
| `UpgradeView::research_icon/_tip/_ubertip/_hotkey` (+`requires`) | the research card uses `Researchart`/`Researchtip`/`Researchhotkey` where present and `Art`/`Tip`/`Hotkey` otherwise |
| `AbilityView::research_icon` | hero learn buttons use `Researchart` (`[AHab]` passive art vs. learn-button art) |
| `AbilityView::base_code/base` + `resolved_name/_icon/_hotkey/_tip/_tooltip` | variants store only the diff (`[AIa1]` has `Art`+`EditorSuffix`, `[AIab]` has `Name`); name coverage rose 278 → 393 of 397 |
| `object()` falls back to the row's prototype (`ObjectDataStore::prototype_of`) | custom map rows only store their changes; without the link a custom unit/item had no icon even though its prototype has one |
| buffs modelled from the profile text (`buff_ids`, `buff`, `BuffInfo`) and `w3b` routed into `BuffStore` | retail ships no buff sheet (0 hits for `AbilityBuffData` in both listfiles); `BuffStore::apply` was dead code, so `war3map.w3b` overrides were dropped |

| `UnitView::{tooltip, proper_names, score_screen_icon, revive_tip, unhotkey}` | the hover/score-screen/revive text that sat unused in the shipped profile files |
| `coverage.rs` + `data_coverage`/`coverage_probe` examples | the audit itself: per class/race counters, missing-id lists, card reachability, requirement resolution |

## Limits of this report

- Numbers are for **this** archive (`War3.mpq`, sha256 above). A 1.27+/1.33 install
  has more rows; the audit is a tool (`data_coverage`) so it can be re-run.
- The baseline note attached to this task said "463 unit rows"; the loader measures
  **466** `UnitData` rows in this archive and the count is pinned by test. The 463
  figure is not reproducible from the installed file and is treated as superseded.
- TFT text cannot be measured without `War3xlocal.mpq`; the report states exactly
  what TFT does resolve and the test pins the absence.
- `war3map.w3d` (doodad object data) and `war3map.w3h` (buff object data) are
  parsed by the corpus gate and used through the same `ObjectDataFile` merge, but
  this report measures their *parse* completeness, not a per-map doodad card
  (doodads have no card; they are terrain decoration with models, 278/278 named
  and 278/278 modellable).
